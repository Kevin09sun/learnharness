# Test Prep Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a third session type, Test prep, that builds a reviewed plan of sections/points from the learner's folder, diagnoses each point with quick short-answer questions, fixes only the gaps, and tracks per-point readiness across sittings.

**Architecture:** A pure core module owns statuses, transitions, readiness and question order. A small file store keeps one JSON per test under `data/tests/`. Each sitting is its own chat (`kind: "testprep"`, `testId` link), so "a later sitting" = a different chat id. A dedicated `testprep` agent gets four tools (`propose_plan`, `test_progress`, `check_point`, `record_result`) plus the read-only file tools. `check_point` is an explain-shaped question (like `recall`) whose committed answer is never revealed. UI adds a plan-review card, a readiness page and a Test prep start mode.

**Tech Stack:** Next.js App Router (read `node_modules/next/dist/docs/` before touching `app/` — see AGENTS.md), React, TypeScript, typebox, pi-agent-core tools, `node:test` via `tsx`.

**Spec:** `docs/superpowers/specs/2026-11-10-test-prep-design.md`

## Global Constraints

- Point statuses are exactly: `unchecked`, `solid`, `gap`, `fixed-recheck`.
- Readiness = solid points ÷ all points (overall and per section); 100% = every point solid; a test/section with 0 points has readiness 0.
- A `fixed-recheck` point becomes `solid` only on a correct answer in a **different sitting (chat id)** than the one that fixed it.
- "I don't know" / help requests count as wrong (→ `gap`); there is no hint step and no self-certification.
- Continue order: re-checks due (fixed in an earlier sitting) → unchecked (interleaved across sections) → gaps.
- Correct answers: ✓ only — the committed answer is never shown. Wrong answers: short explanation (includes the answer) then a fresh question.
- No performance data in the knowledge graph. Test prep sessions **do** run normal graph extraction (like Teach).
- Progress lives in `data/tests/<id>.json` (via `LH_DATA_DIR` seam), separate from chats and graph.
- No change to Teach or Practice behavior.
- Run `npm run typecheck`, `npm run lint` and the touched tests before every commit. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. `record_result` / `check_point` called before the plan is confirmed, or with a point id not in the plan → refused with a retryable tool error, record unchanged. (Task 4 tests)
2. A point fixed and then answered correctly **in the same sitting** stays `fixed-recheck`; readiness does not rise. (Task 1 tests)
3. Plan edited from the readiness page after progress exists: unchanged point ids keep status/history; new points start `unchecked`; removed points leave readiness; 0-point test reads 0 not NaN. (Task 1 + Task 2 tests)
4. A plan edit made in the UI while a sitting is open is not reverted by the next `record_result` (store does fresh read-modify-write per mutation). (Task 2 test)
5. `propose_plan` with no sections, an empty section, or a blank point → refused, so the agent must ask the learner for scope instead of proposing nothing. (Task 4 tests)

  export interface TestPoint { id: string; text: string; source: string; status: PointStatus; fixedIn?: string; history: PointAttempt[] }
  export interface TestSection { id: string; title: string; points: TestPoint[] }

  export function readiness(test: Pick<TestRecord, "sections">): { overall: number; sections: Array<{ id: string; title: string; solid: number; total: number; ratio: number }> }

**Doctrine content (exact rules; wording is the implementer's):**
1. First turn: read the folder the learner gave (outline first; slides only if no outline or it is vague). Propose sections = outline headings, points = individual testable items, each with `source` = the outline line or slide it came from. If neither yields a defensible scope, ask the learner what the test covers — never invent scope. Call `propose_plan`, then stop.
2. After confirmation and at the start of every sitting: call `test_progress`, then work the queue in order.
3. One `check_point` per point, short typed answer. Essay subjects use small skills (thesis for a prompt, analyze a quote, choose evidence; explain a concept, lay out an argument, give an objection) — never a full essay.
4. Grade strictly against the committed answer; then `record_result`. Correct → say only that it's right (✓) and move on; never explain. Wrong / "I don't know" / a request for help or the answer → `record_result` with `wrong`/`dontKnow`, a short explanation including the right answer, then a **fresh** `check_point` on the same point. Still wrong → a different angle.
5. Never credit a self-assessment ("I know this"); no hints.
6. Never mention statuses as scores in prose beyond the readiness the tools report.
